# PMA App Full Application Security Audit (`v2.0.132+2145` @ `ef61936`)

## Summary
- **Verdict**: **FAIL (`P0` Blocker — Score: 38/100)**. `HEAD ef61936` contains **10 new verified findings** (`5 P0` [3 Critical, 2 High], `2 P1` [2 Medium], `3 P2` [3 Low]) plus **8 still-open findings** carried over from the `2026-10-22` and `2026-11-04` audits.
- **Top Risk 1 (`SEC-01`, Critical / `P0`)**: Unsanitized PostgREST `or=()` filter interpolation in `AuthRepository.loginWithPassword` (`lib/data/repositories/auth_repository.dart:44-48, 61`) permits wildcard (`*`/`%`) and operator (`,`) injection with client-side case-insensitive plaintext password comparison.
- **Top Risk 2 (`SEC-02`, Critical / `P0`)**: `supabase/functions/pos-locations/index.ts:273-317` enforces `verifySpv()` on `upsert` and `delete` but completely omits `verifySpv()` on `action === 'import'`, letting any unauthenticated caller write up to 50 POS rows per call via `SUPABASE_SERVICE_ROLE_KEY`.
- **Top Risk 3 (`SEC-03`, Critical / `P0`)**: `supabase/functions/ai-vision/index.ts:50-118` runs with `--no-verify-jwt` and no `APP_PROXY_SECRET` enforced, forwarding arbitrary caller JSON bodies verbatim (`rawBody`) to Google Gemini (`GEMINI_API_KEY`) after buffering up to 12 MB in memory prior to size validation.
- **Attendance Integrity & Client Trust (`SEC-04`, `SEC-05`, `SEC-06`)**: Session state (`flutter.bss_current_user`) and SPV vs. technician authorization are trusted purely on the client, and offline clock tampering / GPS fallback silently burn official POS coordinates onto attendance photos without any watermark warning.

1. **Attendance Records & Watermarked Proof Photos**: Timestamp, GPS coordinates, POS verification status, technician identity/NPP, and camera proof images stored locally (`SharedPreferences`, `IndexedDB`, system gallery) and shared to WhatsApp/Telegram.
2. **Daily Tasks & Proof Bucket (`daily_tasks_manado`, `daily_tasks_bali`, `daily_tasks_ho`, Storage bucket `task-proofs`)**: Branch task dispatches, transfer audit trails, completion reports, and uploaded JPEG proofs.
3. **Maintenance Logs & POS Master Data (`maintenance_logs_manado`, `pos_locations`, Google Sheets webhook)**: Preventative/corrective maintenance records, branch attribution, and official POS geofence coordinates.
4. **User Credentials (`public.app_users` & Offline Fallback Accounts)**: SPV and technician usernames, emails, roles, branch assignments, and passwords.
5. **Cloud API Keys & Service Role Credentials**: `GEMINI_API_KEY`, `GEMINI_API_KEY_FALLBACK`, and `SUPABASE_SERVICE_ROLE_KEY` inside Supabase Edge Functions (`ai-vision`, `pos-locations`).

## Needs Aan decision

1. **Offline Login Mode (`KNOWN-02` / `SEC-01`)**: Should offline password login be removed completely on Web PWA and restricted on Android to previously authenticated sessions (cached token after at least one online login), so hardcoded SPV and technician passwords can be deleted from `auth_repository.dart`?
2. **GPS Fallback & Mock Location Policy (`SEC-06`)**: When a technician's GPS cannot lock indoors (`isDefaultFallback == true`) or when a mock-location app is detected (`isMockLocation == true`), should the app **hard-block** attendance capture, or allow capture with a prominent red warning banner (`GPS FALLBACK / MOCK GPS`) burned permanently into the photo watermark?
3. **Auto-Save to Public Phone Gallery (`SEC-10`)**: Should attendance photos continue to be saved automatically to the phone's public `'BSS Parking'` gallery album on every capture, or only exist inside app-private storage (cleaned after 7 days) after sharing to WhatsApp/Telegram?
4. **Public Visibility of `task-proofs` Bucket (`KNOWN-05`)**: Do proof photo URLs need to remain publicly accessible without authentication (e.g., for external WhatsApp link previews), or can `task-proofs` be switched to signed URLs with expiry?

## Not checked

- **Live Destructive Write/Delete Mutations against Production Supabase & Google Sheets**: Per audit rules (`READ-ONLY AUDIT: never write to Supabase or any remote`), `INSERT`/`UPDATE`/`DELETE` policies on `daily_tasks_*`, `maintenance_logs_manado`, `app_users`, `task-proofs`, and the Google Apps Script webhook were verified via SQL policy definitions (`docs/sql/*.sql`, `supabase/migrations/*.sql`), Edge Function source code, and non-destructive validation probes (`GET`/`HEAD` and empty-payload `POST` validation checks) rather than writing or deleting live production records.
- **Live PostgreSQL `pg_policies` System Catalog Introspection via `supabase db` CLI**: The local repository does not have a `supabase/.temp` linked DB session or database password configured, so RLS state was verified by combining the SQL migration files in `docs/sql/` and `supabase/migrations/` with read-only PostgREST/Storage HTTP probes against `https://sxsjixnnlzhjinzcyhjb.supabase.co`.
- **Dynamic Runtime Instrumentation on Physical Android Device**: Android IPC (`MainActivity.kt`, `FileProvider`, `AndroidManifest.xml`, `network_security_config.xml`) was audited statically from source rather than attaching Frida/adb on a physical handset.
